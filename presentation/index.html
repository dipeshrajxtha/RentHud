Why Modular Monolith over Microservices?
  • No Network Overhead: Direct in-process domain service calls avoid HTTP/gRPC serialization latency.
  • True ACID Transactions: Tenancy creation, agreement generation, and unit status transitions occur in atomic database transactions.
  • Single Source of Truth: Shared contracts in shared/ define strict Zod schemas and TypeScript types for web and API.
  • Simplified DevSecOps: Unified Docker deployment, streamlined database migrations, and unified audit trails.

Core Structural Invariants

Traditional apps conflate the physical building with the rental unit. RentHub enforces strict separation:

  • Landlord: Owns multiple physical properties.
  • Property: Physical asset tied to geospatial coordinates (lat/lng), street address, and building amenities.
  • Property Unit / Floor: Rentable entity (Floor #, unit ID, bedrooms, rent price, deposit).
  • Tenancy: Contractual lease attached strictly to a Unit, never the whole property.

Academic Rigor & Data Integrity
The "One Active Tenancy" Invariant
Mathematical Guarantee
PostgreSQL Partial Unique Index Specification

Application-level checks are vulnerable to concurrency races. RentHub enforces lease exclusivity at the physical storage engine:

CREATE UNIQUE INDEX idx_one_active_tenancy_per_tenant ON tenancies (tenant_id) WHERE status IN ('active', 'pending_signature');
  • Why include pending_signature? If a tenant could sign multiple agreements simultaneously, they could freeze units off the market, causing financial harm to landlords.
  • Historical Preservation: Completed leases ('completed') and early terminations ('terminated_early') are excluded from the index, allowing infinite audit records.
Concurrency Defense Matrix
RACE ATTACK SCENARIO:
Two landlords approve the same tenant's applications at t = 0.001s concurrently.
DATABASE ENGINE ARBITRATION:
The first transaction commits; the second immediately hits PostgresError 23505 (unique_violation) and cleanly aborts with 409 Conflict.

/* Spatial query using GiST index on WGS84 coordinates */ SELECT p.id, p.title, p.address, ST_Distance(p.location, ST_MakePoint($userLng, $userLat)::geography) AS distance_meters FROM properties p JOIN property_units u ON u.property_id = p.id WHERE u.availability_status = 'AVAILABLE' AND ST_DWithin(p.location, ST_MakePoint($userLng, $userLat)::geography, $radiusMeters) ORDER BY distance_meters ASC;

2. Unit Availability Synchronization
  • AVAILABLE: Unit is visible in public PostGIS spatial map search.
  • RESERVED: Landlord has accepted application; locked from other applicants.
  • PENDING_SIGNATURE: Contract issued; locked from public view.

  • Google-Only Auth: Eliminates plaintext password storage, brute-force risks, and password resets entirely.

Evaluation & Critical Analysis
Technical Challenges & Engineering Lessons
Academic Critical Thinking
Challenge 1: Spatial Projections
Geometry vs Geography

Standard Euclidean Cartesian geometry fails across earth curvature. Resolved by enforcing GEOGRAPHY(Point, 4326) which calculates accurate Great-Circle distances natively in meters.

Challenge 2: Cross-Platform Types
TypeScript & Flutter Parity

Preventing schema drift between React and Flutter. Solved via a Single Source of Truth architecture: OpenAPI 3.1 specifications auto-generating Dart models while Zod handles Web/API runtime validation.

Challenge 3: Race Conditions
Approval Concurrency

Multiple approval attempts on the same unit. Solved by replacing optimistic application locking with explicit database row-level locking (SELECT ... FOR UPDATE) and partial unique indexes.
